 F3  CROSS-PLATFORM CIPHER — mobile -> web messages render as "[encrypted]"
================================================================================
 User item 3. Do this FIRST: until it lands, no cross-device test in F1/F2/F4/F5
 can be trusted, because every mobile->web message is an opaque placeholder.

 SYMPTOM
   "When I send a message from the mobile app to the website, everything
   (messages, chats, etc.) appears encrypted."

 VERIFIED BASELINE
   The two clients seal message bodies with TWO DIFFERENT, MUTUALLY
   UNINTELLIGIBLE ciphers that merely share a key-derivation *label*.

   Web  - clients/web/src/worker/db.worker.ts:22-50
          key  = WebCrypto SHA-256("wa-dev-conv-v1:" + conversationId)
                 imported as an AES-GCM CryptoKey
          wire = iv(12) || AES-GCM ciphertext(with 16-byte GCM tag)
          open = crypto.subtle.decrypt; a throw leaves the body undefined,
                 which the repo renders as the "[encrypted]" placeholder
                 (db.worker.ts:56-66)

   Mobile - clients/mobile/src/services/convCrypto.ts:1-96
          key  = hash("wa-dev-conv-v1:" + conversationId) where hash() is a
                 NON-CRYPTOGRAPHIC FNV-1a seed -> xorshift32 PRF (line 13-31)
          wire = nonce(12) || mac(8) || XOR-keystream ciphertext (line 71-80)
          open = openForConversation, throws on bad MAC (line 82-96)
          used at appServices.ts:152-165 (inbound) and :190-197 (outbound)

   So both the KEY BYTES and the WIRE FORMAT differ. A mobile envelope handed
   to the web worker is `nonce||mac||ct` fed to AES-GCM under a different key:
   it always throws, always falls back to the placeholder. The reverse
   direction fails on the MAC check for the same reason. This is 100 % of the
   reported symptom — there is no partial decode, no ordering issue, nothing
   intermittent.

   Why mobile diverged: React Native has no WebCrypto (convCrypto.ts:1-2). That
   constraint is real; the response to it was a second cipher rather than a
   shared one.

 ROOT CAUSE
   Two independent dev ciphers for one wire protocol. Fix = exactly one.

 IMPLEMENTATION
   1. Create the single shared implementation in the package both clients
      already depend on: clients/packages/crypto-wrapper/src/convCipher.ts
      (new). Export `sealForConversation(conversationId, plaintext)` and
      `openForConversation(conversationId, envelope)`, re-exported from
      crypto-wrapper/src/index.ts.

   2. Choose ONE wire format and ONE key derivation and write them down in the
      file header as the normative spec, with a version byte so a future
      change is detectable rather than silent:

        key    = SHA-256("wa-dev-conv-v1:" + conversationId)      -> 32 bytes
        wire   = 0x01 || nonce(12) || AES-GCM(key, nonce, plaintext)
        AAD    = the version byte, so a downgrade cannot be spliced

      Prefer AES-GCM (the web's current choice): it is a real AEAD, it is what
      the eventual libsignal seam looks like, and keeping it means the web's
      existing sealed history stays readable except for the added version byte
      (see step 5 on migration).

   3. Give React Native a real AES-GCM. In order of preference:
        a. `expo-crypto` / `react-native-quick-crypto` if either is already a
           dependency or is trivially addable — check clients/mobile/package.json
           FIRST and reuse what is there.
        b. Otherwise a pure-JS AES-GCM from a maintained, audited library
           (e.g. @noble/ciphers). This is NOT hand-rolling: it is depending on
           a reviewed implementation, which the coding standard permits.
      Do NOT reimplement AES. Do NOT keep the xorshift PRF.
      Express the platform difference as a small injected port
      (`SubtleLike` / `AesGcm` interface) so convCipher.ts itself is
      platform-free and unit-testable in Node.

   4. Rewire both call sites:
        - clients/web/src/worker/db.worker.ts — delete the local convKey/seal/
          openSealed (lines 20-50) and import from crypto-wrapper.
        - clients/mobile/src/services/appServices.ts:152-165 and :190-197 —
          import from crypto-wrapper.
        - DELETE clients/mobile/src/services/convCrypto.ts and its test; move
          any still-valuable test cases into the new shared test file.

   5. Migration of already-stored web history: the version byte means old
      web envelopes (which start with a random IV byte) will not parse. Handle
      it explicitly — on open, if byte 0 != 0x01, try the legacy
      `iv(12)||ct` layout once before giving up. Comment it as a
      time-boxed compatibility shim tied to the dev double, not a permanent
      branch.

   6. While in the decrypt path, fix the placeholder UX: a body that genuinely
      fails to open should render as a distinguishable state ("Message can't be
      decrypted") rather than looking like normal ciphertext text, and should
      log once per conversation so the next occurrence of this class of bug is
      visible instead of silent (the same lesson as C2 in
      Docs/FIX-STATUS-AND-CALLS.md).

 ACCEPTANCE
   AC1  A single module exports sealForConversation/openForConversation; grep
        for `convCrypto` across clients/ returns zero non-test hits.
   AC2  A unit test in crypto-wrapper seals with the web adapter and opens with
        the RN adapter, and vice versa, for: ASCII, emoji, 4-byte UTF-8, empty
        string, and a 64 KB body. All round-trip byte-identically.
   AC3  A tampered envelope (any single flipped bit in nonce, tag, or
        ciphertext) throws on open in both adapters.
   AC4  An envelope sealed for conversation A does not open for conversation B.
   AC5  LIVE: log into web as user A and mobile as user B on the same stack.
        Send mobile -> web: the web thread renders the plaintext, not
        "[encrypted]". Send web -> mobile: same. Both directions, text with
        emoji included.
   AC6  A message that truly cannot be decrypted renders as an explicit
        "can't be decrypted" state and emits exactly one warning per
        conversation, not one per message.

 VERIFY
   cd clients && pnpm -r typecheck && pnpm -r test
   Live: ./start.sh, two devices, the AC5 exchange in both directions.

 OUT OF SCOPE
   No libsignal. No X3DH, no Double Ratchet, no per-device sessions, no key
   directory — this task swaps two dev doubles for one, nothing more. The real
   E2EE work stays where it is (crypto-wrapper/src/engine.ts, cipher.ts).
   No change to media encryption (@wa/media-pipeline) — media already shares one
   path.

 F4  MULTI-DEVICE SYNC — same account on phone + web must stay in step
================================================================================
 User item 4. Depends on F3 (otherwise the synced copies arrive as placeholders).

 SYMPTOM
   "If the same account is logged in on both the mobile app and the website,
   chats should sync in real time across both devices."

 VERIFIED BASELINE
   The SERVER half is already correct and must not be rebuilt:
     server/internal/chat/adapters/pg.go:62-69 — the recipient set is every
     active device of every conversation member MINUS the sending device, so
     the sender's OTHER devices already receive an inbox row:
       "SELECT d.id FROM conversation_members cm JOIN devices d
        ON d.user_id = cm.user_id
        WHERE cm.conversation_id = $1 AND d.revoked_at IS NULL AND d.id <> $2"
     server/internal/chat/service.go:186-204 then publishes a live delivery to
     each of those device ids.

   Two CLIENT defects break it:

   D1 - every inbound item is assumed to be from the peer.
        clients/web/src/services/appServices.ts:578
          for (const it of b.items) this.peerByConv.set(it.conversationId, it.senderUserId);
        with the comment "Inbound items are always from the peer (I never
        receive my own)". That premise is false the moment a second device
        exists. A self-sync copy therefore (a) overwrites the conversation's
        peer id with MY OWN user id, corrupting the header name, presence
        subscription and typing target, and (b) falls through to the unread/
        notification block at :581-600, so the web toasts and unread-badges the
        user's own message sent from their phone.

   D2 - the web has no durable message store, so "sync" cannot survive a reload.
        clients/web/src/worker/db.worker.ts:10 instantiates MemoryMessageRepo
        (clients/packages/client-core/src/memoryRepo.ts:1-5 — "in-memory
        MessageRepo ... until the OPFS SQLite-wasm store lands"). Combined with
        ACK-after-persist (wsClient.ts:233-237 sends client_ack once
        onInboxBatch resolves, and server AckDelivered DELETEs the covered inbox
        rows — server/internal/chat/service.go AckDelivered +
        adapters/pg.go:305), a browser refresh does not merely lose the local
        cache: the server copy is already gone. Web chat history is
        PERMANENTLY LOST on reload. Mobile does not have this problem — it uses
        the real SQLite MessageStore (mobile/src/services/appServices.ts:90-92
        via platform/expoSqlite.ts).

   The SqliteDB port that a web store must satisfy already exists:
   clients/packages/client-core/src/ports.ts:55-59 (exec/run/all).

 ROOT CAUSE
   Client-side, not server-side: a false "inbound == from peer" assumption, plus
   a non-durable web store that discards history the server has already deleted.

 IMPLEMENTATION
   Part A — self-sync correctness (both clients)
   1. Add `myUserId()` to the web AppServices the way mobile already has it
      (mobile/src/services/appServices.ts:113-125 decodes the JWT `sub`).
      Reuse that decode; do not duplicate it — lift it into client-core.
   2. In each onInboxBatch handler, split items into `fromSelf` and `fromPeer`:
        - fromSelf: persist and render as an OUTGOING message (right-aligned,
          own bubble, correct ticks). Never set peerByConv from it. Never
          increment unread. Never toast. Never fire the auto-responder.
        - fromPeer: existing behaviour unchanged.
      Web: clients/web/src/services/appServices.ts:576-606.
      Mobile: clients/mobile/src/services/appServices.ts:152-165.
   3. Confirm the store renders a self-copy on the correct side. Check
      MessageStore/MemoryMessageRepo's `fromMe` determination
      (clients/packages/client-core/src/db/messageStore.ts, planInboxBatch) and
      make it key on sender USER id vs my user id, not on device id or on
      "arrived via inbox".
   4. Extend the same self/peer split to receipts, reactions, edits, deletes and
      read-state so a chat read on the phone stops showing unread on the web.

   Part B — durable web store
   5. Implement an OPFS SQLite-wasm adapter satisfying SqliteDB
      (ports.ts:55-59): new clients/web/src/worker/opfsSqlite.ts using
      @sqlite.org/sqlite-wasm with the OPFS VFS, opened inside the existing
      dedicated worker (it is already the right thread).
   6. Swap MemoryMessageRepo for `new MessageStore(db, cursors)` in
      clients/web/src/worker/db.worker.ts:10 — the SAME class mobile uses, so
      schema, merge semantics and search are shared, not re-derived.
   7. Keep MemoryMessageRepo as the unit-test double and as an automatic
      fallback when OPFS is unavailable (private windows, older Safari); log
      once, loudly, when the fallback engages, because in that mode reload
      still loses history.
   8. Verify the cursor path end-to-end: on boot the web must send its persisted
      cursors in `hello` (SessionProvider.cursors at appServices.ts:568 currently
      returns `this.cursorMirror` — make that mirror load from the store, as
      mobile does with store.cursorSnapshot() at mobile appServices.ts:143).
      Without this, resume replay re-sends or skips.

 ACCEPTANCE
   AC1  With the same account on web and mobile, a message SENT from mobile
        appears in the web thread within 1 s, on the OUTGOING side, with no
        unread badge and no toast.
   AC2  The reverse (sent from web, appears on mobile as outgoing) holds too.
   AC3  A message from the real peer still increments unread and toasts, on
        both clients.
   AC4  Reading a chat on one device clears its unread badge on the other.
   AC5  Reload the web page: full chat history is still present, in order,
        decrypted. Close the tab for 5 minutes, send from mobile, reopen the
        web: the missed messages arrive exactly once (no duplicates, no gaps).
   AC6  The conversation header on web shows the PEER's name after a self-sync
        copy arrives — not the user's own name.
   AC7  When OPFS is unavailable the client still works, logs one explicit
        warning, and says so rather than silently losing data.

 VERIFY
   cd clients && pnpm -r typecheck && pnpm -r test
   Live: two devices on one account, run AC1-AC6 by hand. For AC5, confirm with
   DevTools > Application > OPFS that the database file exists and grows.

 OUT OF SCOPE
   No changes to server fan-out — it is already correct. No device-linking UX
   (that is T3.01, already built). No history-transfer bootstrap for a NEWLY
   linked device (that is @wa/sync-engine, T3.02) — this task is about two
   devices that are both already linked and online.

 F5  LATENCY — messages arrive late; target is WhatsApp-class realtime
================================================================================
 User item 5.

 SYMPTOM
   "Messages are being delivered late. Check why there is a delay and fix it. I
   want real-time, low-latency communication similar to WhatsApp."

 TARGET (already specified in this repo — do not invent a new one)
   Docs/01-requirements/non-functional-requirements.md:17 — NFR-05, message
   end-to-end latency with both parties online, same region:
   p50 <= 150 ms, p95 <= 500 ms.

 VERIFIED BASELINE — the transport is push-based, so "late" is not architectural
   Send:    client WS `msg_send` -> ws-gateway -> core-api AcceptMessage ->
            PG transaction (seq + inbox rows) -> NATS `dev.{id}.out` per
            recipient device -> gateway subscription -> recipient WS.
   Sources: server/internal/gateway/server.go:419-420 (frame dispatch),
            server/internal/chat/service.go:152-204 (accept + publish),
            server/internal/gateway/delivery.go (per-device subscription),
            server/cmd/ws-gateway/main.go:108 (real NATS source, not the
            in-memory one), server/cmd/core-api/main.go:489 (NATS publisher).
   The UI is event-driven too: clients/web/src/ui/screens.tsx:809/5144 subscribe
   via services.onChange and the 5 s setInterval next to them is labelled
   "safety net for missed signals", not the primary path.

   So there is no polling loop to blame. MEASURE FIRST. The four concrete
   suspects, in the order they are most likely to matter:

   S1 - the gateway read loop is synchronous per frame.
        server/internal/gateway/server.go:419-420 calls handleMsgSend inline in
        the read loop, and handleMsgSend (:452-457) opens a context with
        rpcTimeout = 2s (server.go:23-24) around the core-api call. One slow
        AcceptMessage therefore head-of-line-blocks EVERY subsequent frame on
        that connection for up to 2 s — sends, receipts and acks alike. Under
        any burst this is the dominant term.
   S2 - link-preview fetch on the send path.
        clients/web/src/services/appServices.ts:656-659 and
        clients/mobile/src/services/appServices.ts:190-193 both `await
        generateLinkPreview(...)` BEFORE enqueueing and before the optimistic
        render. It short-circuits with no URL
        (packages/media-pipeline/src/linkPreview.ts:132-133), but any message
        containing a link blocks on a third-party HTML fetch with no visible
        timeout — the user watches their own message hang.
   S3 - per-send PG work.
        chat/adapters/pg.go:44-120 does, in one transaction: seq assignment, a
        recipient-device JOIN, and a pgx.Batch of N INSERTs. Check for a missing
        index on the recipient JOIN and on `message_inbox(recipient_device_id,
        conversation_id, seq)`, and confirm the accept transaction is not
        holding a lock across the NATS publish.
   S4 - receipt coalescing adds a deliberate 250 ms.
        server/internal/gateway/receipts.go:13 receiptFlushInterval = 250ms.
        This is correct for receipts (it is what stops tick storms) but if any
        MESSAGE path shares that ticker it must not.

 IMPLEMENTATION
   1. INSTRUMENT BEFORE CHANGING ANYTHING. Add a per-message timing trail with
      the existing observability stack (ops/dashboards, server/internal/platform):
      client send -> gateway receive -> core-api accept start/end -> PG commit ->
      NATS publish -> gateway deliver -> client render. Emit a Prometheus
      histogram for each hop plus the end-to-end total. Without this you are
      guessing, and the answer will be different on the dev rig than in staging.
   2. Reproduce with numbers: two clients on the live rig, 100 messages, record
      p50/p95 per hop. Write the measured table into this task's completion note.
      That table decides what to fix.
   3. Fix S1 unconditionally — it is a correctness-of-design issue regardless of
      what the numbers say. Dispatch handleMsgSend onto a bounded per-connection
      worker (or an errgroup with a small concurrency limit) so a slow RPC never
      blocks the read loop, while PRESERVING per-connection send ordering
      (messages from one device must keep their order). Keep the 2 s timeout.
   4. Fix S2 unconditionally: enqueue and render optimistically FIRST, then
      generate the preview asynchronously and attach it as an update. Give
      fetchHtml an explicit timeout (2 s) and cap the body size. A link must
      never delay the message.
   5. Fix whatever else the measurements indict — index the hot queries, or move
      the fan-out off the accept path — but only with a before/after number.
   6. Add a latency SLO alert if one does not already exist for NFR-05
      (ops/alerts already has a message-latency runbook per Docs/TASKS.txt T4.08
      — wire the alert to the new histogram if it is dangling).

 ACCEPTANCE
   AC1  A Prometheus histogram exists for each hop named above, and a dashboard
        panel shows end-to-end p50/p95.
   AC2  Measured on the dev rig with both clients online, 100 sequential
        messages: p50 <= 150 ms and p95 <= 500 ms end-to-end (NFR-05). Report
        the actual numbers, before and after.
   AC3  handleMsgSend no longer blocks the connection read loop; a test proves
        that a deliberately slow AcceptMessage (injected fake, 1.5 s) does not
        delay an unrelated frame on the same connection beyond ~50 ms.
   AC4  Per-connection send ORDER is preserved under concurrency — a test sends
        20 messages back-to-back on one connection and asserts monotonically
        increasing seq.
   AC5  Sending a message containing a URL renders optimistically in < 50 ms;
        the preview attaches afterwards. A link host that never responds delays
        nothing and times out at 2 s.
   AC6  No regression in the durability invariant: zero loss, zero duplicates
        (the ops/loadtest auditor's msgs_lost == 0 rule).

 VERIFY
   cd server && go build ./... && go vet ./... && go test ./...
   cd clients && pnpm -r typecheck && pnpm -r test
   Live: the AC2 measurement run, numbers recorded.

 OUT OF SCOPE
   No transport rewrite (no QUIC, no custom protocol). No change to the relay
   model or to ACK-after-persist. Do not "fix" the 250 ms receipt coalescing —
   it is deliberate and correct; only prove messages do not ride it.
